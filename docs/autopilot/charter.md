# 自走改善の憲章

ユーザーの指示が無くても、シティビルダーズのクオリティを上げ続けるための取り決め。
次の実行はここから読み始める。

## 最上位のゴール（2026-10-10 ユーザー指示）

「プレイヤーが**楽しい**と思える／**お金を払いたい**と思える／**ハマって続けたくなる**」ゲームにする。
これを `charter` の他の全項目より上に置く。個別の基準（演出の秒数、勝率）はこのための手段。

- 続けたくなる仕組みは、**良い設計**で作る: 上達の実感、読み合いの深さ、短い 1 試合、
  「もう 1 戦」の気持ち、集める・育てる進行、毎日戻る理由。
  プレイヤーを騙す・煽る・不利益を隠す類（ダークパターン）は使わない。
- 「お金を払いたい」は、**払う価値が見える**ことで作る（見た目の収集、拡張、広告なしなど）。
  実際の課金・決済の実装は、ユーザーに相談してから。設計の案までは自走でよい。

## PDCA を止めない（ユーザー指示）

**調査 → 計画 → 実施 → 検証 → 反映 → 調査 …** を、ユーザーの指示を待たずに回し続ける。
止まるのは、トークンが尽きる時か、ユーザーが止めた時だけ。確認待ちで止まらない。
ユーザーのフィードバックが来たら取り込むが、来ないことを前提に進める。

1 周の中身:
1. **調査**: 今のゲームの一番の弱点は何か。他のゲーム・プレイヤーの声・自己対戦の数字から見つける。
2. **計画**: 効果が大きく、検証できる 1〜3 件を選び、backlog の上に置く。
3. **実施**: タグを打ってから変える。
4. **検証**: テスト、自己対戦、画面の確認（preview）。数字で前後を比べる。
5. **反映**: 良ければ公開（`npm run deploy`）。悪ければ戻す。journal に書く。
6. **次の調査**へ。周の終わりに必ず次の周を始める。

## 並列と分担

- 調査・計測・素材づくりのように独立した作業は、**サブエージェントに並列で任せる**。
  難しい設計判断・企画の評価には `model: opus` を使ってよい。単純な調査は sonnet/haiku でよい。
- サブエージェントには、背景・目的・触ってよい範囲・返してほしい形を渡す。結果は鵜呑みにせず、
  数字は自分で再確認してから採用する。
- 同じファイルを同時に触らせない。コードを書かせるときは `isolation: worktree`。

## 目標

クラロワ級の画面・音・手触りと、カードゲームとしての読み合いの深さ。

**ゲームの核（守る）**: 相手の手を読んで、妨害と投資のタイミングを競う。
それにより自陣営が発展していく気持ちよさ。

**既知の弱点（ユーザー指摘）**: 戦略がワンパターン。強いカードと弱いカードがあり、
結局お金を稼ぐ系が強い。

## 許可（ユーザーが明示済み）

- 画面・音・演出・UI・カード効果・ルール・バランス、すべて変更してよい。
- 修正のたびに公開まで通してよい（`npm run deploy`）。
- 条件: 毎回、戻れるバックアップを取ってから変える（下記）。
- 守る: 核を壊さない。ルールを変えたら journal に理由と前後の数字を残す。

## バックアップ

変更の前に必ずタグを打つ。壊れたらタグに戻す。

```bash
git tag autopilot/<連番>-<短い名前>   # 例: autopilot/012-before-card-rework
```

履歴の書き換え（force push、reset --hard の公開ブランチへの適用）はしない。
戻すときは `git revert` か、タグからの新しいブランチで行う。

## 回し方

1. `backlog.md` の一番上を選ぶ（採点が低い項目ほど上）。
2. タグを打つ。
3. 変更する（1 回の実行で最大 3 件）。
4. 測る（`npm run typecheck` / `npm test` / 該当の監査ツール）。
5. 良くなったら公開し、`journal.md` に「何を・なぜ・前後の数字」を書く。
   悪くなったら戻し、失敗として journal に書く。
6. 同じ領域で 3 回続けて改善しなければ、その領域は止めて backlog の下へ。

## 基準の作り方

基準は自分の感覚でなく、**他のゲームから実測して決める**（共通 CLAUDE.md の「実測」）。

- 画面・動き: クラロワ、ハースストーン、マーベルスナップ等の動画・スクショから
  時間・曲線・色・余白を数値で抜き、`refs/` と `standards.md` に残す。
- 音: 1 動作あたりの層の数、長さ、音量差を同様に調べる。
- ゲーム性: 他のカードゲームのコスト曲線、ゲーム長、逆転率、カード採用率の
  目安を調べ、自己対戦（`npm run lab` / `simulate`）の合格ラインにする。
- 基準は固定でない。参考を増やして見直してよい。見直したら journal に書く。

## 素材

- 生成（ChatGPT 画像／ElevenLabs）が主力。画風は既存に合わせる。
- ネット素材は CC0 など再利用が明示されたものだけ。出どころとライセンスを
  `refs/LICENSES.md` に必ず記録する。市販ゲームの素材は使わない。

## 止める条件

- 3 回連続で改善なし → その領域を止めて報告。
- 公開版が壊れたら、最優先でタグへ戻す。
- トークンが残り少なくなったら、変更を途中で放置せず、戻すか完成させて journal を更新して終わる。
